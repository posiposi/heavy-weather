# 概要

引数で受け取ったタスク仕様（自然文）を、3エージェントのチームで実装しきる。

| 役割 | エージェント | 責務 |
|---|---|---|
| implementer | `implementer` | タスク仕様に基づく TDD 実装、およびレビュー指摘の修正 |
| format-checker | `format-checker` | `.claude/rules/` のルールと `gofmt` / `go vet` への適合確認 |
| reviewer | `code-reviewer` | 実装結果への批判的レビュー（設計・不変条件・バグ・セキュリティ） |

format-checker と reviewer は**指摘を返すだけで、コードを修正しない**。修正は必ず implementer に戻す。役割の分離を崩すと、誰が何を直したのか追えなくなり、同じ箇所を二重に書き換える事故が起きる。

オーケストレーション（各エージェントの起動順、指摘の受け渡し、終了判定）はこのスキルを読んでいるメインコンテキストの責務であり、サブエージェントには委譲しない。

## Phase 0: 仕様の確定とタスク登録

1. 引数のタスク仕様を読む。**実装範囲・完了条件が曖昧なまま着手しない。** 解釈が分かれると成果物が変わる点（対象パッケージ、公開する型・関数のシグネチャ、扱う異常系の範囲など）が残っている場合は、`AskUserQuestion` で確認してから進む。ルーチンな判断は自分で決めてよい。
2. `documents/heavy-weather-architecture.md`（設計書）と `CLAUDE.md` を確認し、仕様が設計書 §9 のどの段階に当たるかを把握する。`documents/` は Git 管理外のため手元にないことがある。その場合は設計上の判断を推測で進めず、ユーザーに確認する。
3. `TaskCreate` で実装タスクを1件作成する。以降の全エージェントにこのタスク ID を渡す。

   - subject: タスク仕様の要約
   - metadata: `{"type": "implementation", "spec": "<タスク仕様の全文>"}`

   仕様をタスクに載せるのは、`implementer` が `TaskGet` で仕様を参照する設計になっているため。プロンプトにだけ書くと、修正ラウンドで仕様が失われる。

## Phase 1: 実装（ラウンド 0）

`implementer` エージェントを起動し、TDD サイクルで実装させる。渡す情報:

- 対象タスク ID
- 実施すべき作業（テストコード作成 → RED 確認 → 実装 → GREEN 確認 → lint）
- 「レビューは行わない。他サブエージェントを起動しない」旨

`implementer` は `tdd-workflow` / `linter-execute` スキルを持つため、テスト・lint の手順を再説明する必要はない。

完了したら `TaskGet` で `metadata.implementation_result.files_changed` を取得する。これが以降のレビュー対象となる変更ファイル一覧。

## Phase 2: レビューと修正のループ

ラウンド `n`（`n = 1, 2, 3`）として以下を繰り返す。**1周 = 並列レビュー1回 + 修正1回**。

### 2-1. 並列レビュー

`format-checker` と `code-reviewer` を**同一メッセージ内で並列に起動**する。両者は独立した観点であり、直列にすると待ち時間が倍になるだけで精度は上がらない。

各エージェントに渡す情報:

- 対象タスク ID
- 変更ファイル一覧
- 現在のラウンド番号
- 前ラウンドで自分が出した指摘（2周目以降。同じ指摘を再掲させず、解消されたかを判定させるため）

### 2-2. 終了判定

両方の報告を受け取ってから判定する。片方だけ見て先に進まない。

| 状況 | 対応 |
|---|---|
| format-checker と reviewer の両方が `approved` | **完了**。Phase 3 へ |
| どちらかに指摘がある、かつ `n < 3` | 2-3 の修正へ進み、ラウンド `n+1` を開始 |
| どちらかに指摘がある、かつ `n = 3` | 2-3 の修正を行った後、2-4 の最終確認をして**打ち切り**。Phase 3 へ |

### 2-3. 修正

`implementer` エージェントを起動し、両者の指摘をまとめて渡す。1回の起動で両方の指摘に対応させる（format-checker の指摘と reviewer の指摘は同じファイルの同じ箇所に及ぶことが多く、別々に直すと後の修正が前の修正を打ち消す）。

渡す情報:

- 対象タスク ID
- format-checker の指摘（根拠のルールファイル名を含めたまま渡す）
- reviewer の指摘（`critical` を最優先、`suggestions` は対応可能なもの）
- 「修正後に必ずテストと lint を通すこと」

指摘に納得できない・仕様と矛盾する場合、`implementer` は黙って無視せず、対応しない理由を報告するよう指示する。無言の未対応は次ラウンドで同じ指摘を再生産する。

### 2-4. 打ち切り時の最終確認

3周目の修正を終えた場合のみ、`format-checker` と `code-reviewer` をもう一度並列起動して現状を確認する（これは新しい周ではなく、報告を事実にするための確認であり、この後に修正は行わない）。

ここで残った指摘が「未解決の指摘」である。推測で「たぶん直った」と書かないために、必ずこの確認を経てから報告する。

## Phase 3: 報告

`TaskUpdate` でタスクを `completed` にし、ユーザーへ以下を報告する。

```
## 実装結果
- 変更ファイル: <一覧>
- テスト: <passed / failed（failed なら出力を添える）>
- lint: <gofmt / go vet の結果>

## レビュー経過
- 実施ラウンド数: <n> 周
- 終了理由: 両者承認 / 3周到達による打ち切り

## 未解決の指摘
<打ち切り時のみ。ファイル・指摘内容・なぜ解消しなかったかを1件ずつ列挙する。なければ「なし」>
```

3周到達で打ち切った場合、**未解決の指摘を省略・要約で丸めない**。この報告を見てユーザーが続行を判断するため、残っている問題が見えないと判断材料にならない。テストが落ちたまま終わった場合も同様に、明るく取り繕わず落ちた事実と出力を示す。

## 注意事項

- テスト・lint・ビルドはすべて `docker compose` の `app` コンテナ内で実行する（ホストに Go を入れない構成）。起動していなければ `docker compose up -d`
- コミット（`git add` / `git commit`）はこのスキルでは行わない。実装とレビューの完了までが範囲であり、コミットするかはユーザーの判断
- GitHub Issue 番号を起点とし、タスク分解から PR 作成まで通す場合は、このスキルではなく `implement` スキルを使う
- レビュー観点はエージェント側の定義（`.claude/agents/`）と `.claude/rules/` が持つ。このスキルに観点を書き足すと二重管理になるため、観点を増やしたい場合はエージェント定義かルールを更新する
