# 天気通知システム アーキテクチャ設計

## 1. 要件

### 機能要件

| 項目 | 内容 |
|---|---|
| 日次通知 | 毎朝、指定都市のその日の天気を通知する |
| 降雨時間帯の通知 | 降水確率が高い時間帯を、日次通知の本文に含めて同時に通知する |
| 通知チャネル | メール通知。将来的に push 通知への拡張を想定 |
| ユーザー管理 | 通知対象ユーザーを管理できる |
| フロントエンド | 当面不要。将来的に管理画面を追加する可能性あり |

### 非機能要件

| 項目 | 内容 |
|---|---|
| 言語 | Go |
| インフラ | AWS |
| アーキテクチャ方針 | 可能な限りサーバレスを指向する |

## 2. 全体構成

```
EventBridge Scheduler
        │ 定時起動
        ▼
   Lambda (発行側)  ──▶ RDS         (通知対象ユーザー、購読都市、チャネル設定)
        │            ──▶ 外部天気API (都市単位で予報を取得)
        │ PutEvents
        ▼
EventBridge カスタムバス
        │ ルールで detail.channel を判定
        ├──────────────┬──────────────┐
        ▼              ▼              (将来)
   SQS (メール用)   SQS (push用)
        │              │
        ▼              ▼
   Lambda (送信側)  Lambda (送信側)
        │              │
        ▼              ▼
       SES            SNS
        │              │
        ▼              ▼
      ユーザー       ユーザー
```

現時点ではメール経路のみを構築する。push 追加時は、EventBridge のルール・SQS キュー・送信 Lambda を1組追加するだけで済み、発行側には変更を加えない。

## 3. 処理フロー

| # | 主体 | 処理 | 設計上の要点 |
|---|---|---|---|
| 1 | EventBridge Scheduler | 定時(毎朝◯時 JST)に Lambda を呼び出す | タイムゾーンを `Asia/Tokyo` で直接指定。リトライポリシーと DLQ をスケジューラ側に設定 |
| 2 | Lambda(発行側) | RDS から通知対象ユーザー、購読都市、有効チャネルを取得 | VPC 内に配置。`sql.DB` はグローバル保持し `SetConnMaxIdleTime` を DB の `wait_timeout` より短く設定 |
| 3-a | Lambda(発行側) | 都市を重複排除し、都市単位で外部天気 API を呼び出す | `http.Client` にタイムアウト必須。並行数を制限。都市単位の部分成功を許容する |
| 3-b | Lambda(発行側) | 予報をドメインモデルに変換し、ユーザー × チャネルに展開して EventBridge に `PutEvents` | イベントには整形済み本文を載せず意味データのみを載せる。`notificationId` は入力から決定的に生成 |
| 4 | EventBridge カスタムバス | ルールが `detail.channel` を判定し、対応する SQS へルーティング | 現時点ではメール用ルールのみ作成 |
| 5 | イベントソースマッピング | SQS をポーリングし、バッチにまとめて Lambda を同期呼び出し | `maximumConcurrency` で SES のレート制限に合わせて流量調整。可視性タイムアウトは関数タイムアウトの6倍を目安 |
| 6-a | Lambda(送信側) | 冪等性チェック後、本文を整形して SES に送信 | `ReportBatchItemFailures` で失敗分のみ返す。ハンドラは `error` を返さず `nil` を返す |
| 6-b | SES | 各ユーザーへメールを配信 | 送信ドメイン認証(DKIM / SPF / DMARC)。マネージドテンプレートで本文を管理 |

### 処理順序に関する補足

「ユーザー取得 → 予報取得」の順である点が重要。どの都市の予報を取得すべきかはユーザーの購読情報に依存するため、外部 API 呼び出しはユーザー取得の後になる。

また都市の重複排除を行うことで、ユーザー数に関わらず外部 API の呼び出し回数を都市数に抑えられる。

## 4. 技術選定と根拠

### 4.1 スケジューラ: EventBridge Scheduler

| 候補 | 評価 |
|---|---|
| **EventBridge Scheduler** | **採用。** タイムゾーンをネイティブ指定でき、SQS や EventBridge バスを Lambda を挟まず直接ターゲットにできる。リトライポリシーと DLQ をスケジューラ自体に設定できる |
| EventBridge Rules | cron が UTC 固定。1バスあたりのルール数に上限があり、大量スケジュールに不向き |
| Step Functions の Wait ステート | 動的なスケジューリングには強いが、定時起動には過剰。待機中も実行が継続しコスト構造が素直でない |
| SQS 遅延キュー | 最大15分までのため日次通知には使えない。リトライのバックオフには有用 |
| DynamoDB TTL | 削除タイミングが最大48時間ずれるため通知トリガには使えない |
| ECS / EC2 上の cron | サーバレス指向の非機能要件から外れる |

**将来性の観点:** Scheduler は大量のスケジュールを扱え、one-time スケジュールを実行後に自動削除できる。これにより「ユーザーごとに配信時刻を変える」「降雨予測時刻の直前に再通知する」といった発展が同じ仕組みの延長で実現できる。

### 4.2 データストア: RDS

| 候補 | 評価 |
|---|---|
| **RDS (MySQL / PostgreSQL)** | **採用。** アクセスパターンが未確定であること、データが本質的にリレーショナルであること、管理用途の集計クエリが SQL で書けること、運用の習熟度が判断理由 |
| DynamoDB | VPC 不要で完全サーバレスを維持でき低コストだが、先にアクセスパターンを確定させる必要がある。拡張を前提とすると前提が成立しない |
| Aurora Serverless v2 (最小0 ACU) | 使わない時間帯の課金をゼロにできるが、日次バッチ主体のワークロードでは起動と停止の繰り返しにより逆にコスト増となる可能性がある。再開レイテンシも通知処理に影響する |
| Aurora DSQL | サーバレスかつ PostgreSQL 互換だが、外部キー・トリガー・ビュー・シーケンス・PL/pgSQL などが非対応。「リレーショナルな表現力」を求めて RDS を選ぶ目的と手段が食い違う |

**受け入れるトレードオフ:**

- VPC 前提となり、外部 API 到達のため NAT Gateway の固定費が発生する
- Lambda の同時実行数が接続数に直結するため、同時実行の制御が必要

**緩和策:** Lambda を VPC の内外で使い分ける。AWS サービスへは VPC エンドポイントで到達し、外部 API のみ NAT を通す。

### 4.3 RDS Proxy: 現時点では不採用

| 観点 | 内容 |
|---|---|
| コスト | プロビジョンドインスタンスは vCPU 数に応じた時間課金で、最低2 vCPU 分が発生。小さいインスタンスでは Proxy が DB 本体より高くつく可能性がある。Aurora Serverless v2 と組み合わせる場合は最低8 ACU 分が課金される |
| ピン留め | MySQL ではプリペアドステートメントの利用がピン留め条件に含まれる。Go の `database/sql` は内部的にプリペアドステートメントを使うため、意図せずピン留めが発生し多重化の恩恵が失われる。回避には DSN の `interpolateParams=true` が必要。PostgreSQL は拡張クエリプロトコル対応により条件が緩和されている |
| 必要性 | 本構成では SQS イベントソースマッピングの `maximumConcurrency` により同時実行数を明示的に制限しているため、接続数の上限が設計時点で確定している。解決すべき問題が発生していない |

**将来導入を検討する条件:**

- フェイルオーバー時間の短縮が要件になった場合
- フロントエンドが追加され、API トラフィックが予測不能になった場合
- Lambda から DB 認証情報を排除したい場合(ただし Secrets Manager からの取得とキャッシュでも代替可能)

**Proxy を使わない場合の実装上の注意:**

- `sql.DB` はパッケージレベル変数として保持する(`sql.DB` 自体がコネクションプール)
- `SetMaxOpenConns` を小さく設定する
- `SetConnMaxIdleTime` を DB 側の `wait_timeout` より短くする(Lambda の凍結中に切断された接続を掴む問題の回避)
- Lambda に予約された同時実行数を設定する

### 4.4 Lambda の分割方針

発行側と送信側の2関数構成とする。判断基準は以下の4点。

- 失敗の隔離単位が異なるか
- スケーリング特性が異なるか
- タイムアウトやメモリの要件が異なるか
- 他のユースケースからも再利用されるか

「ユーザー取得 + 予報取得 + イベント発行」はいずれも同一ユースケースの一部であり、まとめてリトライするのが正しいため1関数に収める。一方、発行側と送信側は同時実行数の要件が異なる(送信側は SES のレート制限に従う)ため分離する。

**Lambdalith について:** 単一関数に複数責務を集約する方式は、デプロイ単位が1つになり Go との相性も良い。ただし IAM が最小権限にならない、同時実行数とタイムアウトのつまみが1つしかない、観測性の粒度が落ちるという課題がある。将来フロントエンドを追加する場合は、API 用関数の中を Lambdalith とし、通知パイプラインとは分離する構成が適する。

### 4.5 外部天気 API

| 候補 | 評価 |
|---|---|
| Open-Meteo | `hourly=precipitation_probability` で1時間粒度の降水確率が取得できるため、要件に直接対応する |
| 気象庁 JSON | 無料かつ公的だが、降水確率が6時間粒度で「任意の時間」の解像度としては粗い |

**着手前に実地確認すべき項目:**

- 降水確率が実際に1時間粒度で返るか
- レート制限と利用規約(商用利用の可否)
- タイムゾーンの扱い

## 5. イベント設計

### 5.1 設計原則

**イベントに整形済みの本文を載せない。** メールなら SES のテンプレートに流し込み、push ならタイトルと本文を短く圧縮する、という整形はチャネルアダプタの責務とする。イベント側に HTML 本文を持たせると、push 追加時にイベントスキーマの作り直しが必要になる。

### 5.2 スキーマ例

```json
{
  "notificationId": "01J...",
  "version": "1",
  "userId": "usr_123",
  "channel": "email",
  "type": "daily_weather",
  "payload": {
    "city": "osaka",
    "date": "2026-08-15",
    "tempHigh": 34,
    "tempLow": 27,
    "rainHours": [
      { "from": "15:00", "to": "18:00", "probability": 70 }
    ]
  }
}
```

### 5.3 決定事項

| 項目 | 方針 |
|---|---|
| チャネル選択の責務 | 発行側が設定を読み、`(user × 有効チャネル)` の数だけイベントを発行する。消費側で判定させると全チャネルの消費者が設定テーブルを読むことになり結合が増える |
| 冪等キー | `notificationId` とチャネルの複合。チャネル単位での再試行を可能にするため |
| `notificationId` の生成 | 入力から決定的に生成する(例: `hash(userId, date, type)`)。ランダム生成すると再実行時に別 ID となり、下流の冪等性チェックをすり抜ける |
| スキーマバージョン | `detail.version` を持たせ、後方互換を壊す変更時に消費者を段階移行できるようにする |
| 配信不能のフィードバック | チャネル無効化イベントとして抽象化する。SES のバウンスと push のエンドポイント失効を同じ形で扱う |

## 6. フローに現れない構成要素

| 要素 | 配置 | 目的 |
|---|---|---|
| 冪等性テーブル | RDS(`notificationId` + `channel` の複合ユニーク制約) | SQS の at-least-once による二重送信の防止 |
| DLQ | 各 SQS キューに `maxReceiveCount` 付きで設定 | 送信に繰り返し失敗したイベントの隔離 |
| バウンス / 苦情の受信 | SES → SNS → Lambda | 該当ユーザーのチャネルを無効化し、送信抑制リストを維持する |
| SES `MessageId` の保存 | RDS | バウンス通知と送信レコードの突き合わせ |
| シークレット管理 | Secrets Manager(DB 認証情報)、SSM Parameter Store(天気 API キー) | 初期化フェーズで一度だけ取得しキャッシュする |
| VPC 構成 | 発行側 Lambda は VPC 内、外部 API 向けに NAT Gateway、AWS サービスには VPC エンドポイント | RDS アクセスと外部 API アクセスの両立 |
| 監視 | CloudWatch(`notificationId` を相関キーとした構造化ログ)、DLQ のメッセージ数アラーム | どのユーザーのどの通知が失敗したかの追跡 |

## 7. 実装上の注意点

### 7.1 発行側 Lambda

- **`http.Client` のタイムアウトを必ず設定する。** `http.DefaultClient` はタイムアウトが無限であり、外部 API が応答しない場合に全ユーザーの通知が停止する
- **`PutEvents` は1回10件までで部分失敗があり得る。** レスポンスの `FailedEntryCount` を確認し、失敗したエントリのみ再送する。全件リトライすると重複配信になる
- **API キーは初期化フェーズで一度だけ読む。** ハンドラ内で毎回取得するとレイテンシとコストが実行回数分乗る
- **外部 API 障害時の方針を決めておく。** 天気通知の性質上、部分成功を許容して取得できた都市だけ配信するのが現実的

### 7.2 送信側 Lambda

イベントソースマッピング(AWS が管理するポーラー)が SQS をポーリングし、Lambda を同期呼び出しする。Lambda 関数自身が `ReceiveMessage` を呼ぶわけではない。この構造から以下が導かれる。

- **ハンドラがエラーを返すとバッチ全体がキューに戻る。** バッチ内の成功分も再配信され二重送信になるため、`ReportBatchItemFailures` を有効にし、失敗したメッセージ ID のみ返す
- **その際ハンドラは `error` を返さず `nil` を返す。** エラーを返すと部分バッチレスポンスが無視される
- **可視性タイムアウトは関数タイムアウトより十分長くする**(6倍が目安)
- **DLQ はキュー側に設定する。** Lambda の障害送信先(`onFailure`)とは別の仕組み

```go
func handler(ctx context.Context, e events.SQSEvent) (events.SQSEventResponse, error) {
	var failures []events.SQSBatchItemFailure
	for _, msg := range e.Records {
		if err := sendOne(ctx, msg); err != nil {
			failures = append(failures, events.SQSBatchItemFailure{ItemIdentifier: msg.MessageId})
		}
	}
	return events.SQSEventResponse{BatchItemFailures: failures}, nil
}
```

### 7.3 ハンドラ1件あたりの処理

1. 冪等性チェック(`INSERT ... ON CONFLICT DO NOTHING` 等で「送信中」レコードを立て、既存なら即 return)
2. 本文の整形(SES マネージドテンプレートを使う場合はテンプレート名と差し込みデータを用意)
3. SES 呼び出し(`SendEmail` / `SendTemplatedEmail`)。返却された `MessageId` を保存する
4. 送信済みに更新

## 8. リポジトリ構成

通常の Go プロジェクトとして単一の Git リポジトリで管理する。「Lambda のプロジェクト」ではなく「Lambda にもデプロイできる Go アプリケーション」として扱う。

```
weather-notifier/
├── cmd/
│   ├── publisher/main.go       発行側 Lambda のエントリポイント
│   └── sender/main.go          送信側 Lambda のエントリポイント
├── internal/
│   ├── domain/                 値オブジェクト、降水判定ロジック
│   ├── usecase/                処理の組み立て
│   └── adapter/
│       ├── weather/            天気 API クライアント
│       ├── rds/                UserRepository の実装
│       └── notifier/           SES 送信
├── infra/                      IaC (SAM / CDK / Terraform)
├── Makefile
└── go.mod
```

### 方針

- **ドメイン層は Lambda に依存させない。** `domain` パッケージが `aws-lambda-go` を import していたら設計が誤っているという判定基準になる
- **Lambda を分割してもロジックは共有する。** 分割されるのは `cmd/` 配下のみで、`internal/` は両方から参照される
- **アプリと IaC は同居させる。** この規模ではアプリの変更と Lambda 設定の変更が同時に発生することが多く、リポジトリを跨ぐと変更が分断される

### ビルド

```makefile
build:
	GOOS=linux GOARCH=arm64 CGO_ENABLED=0 \
	  go build -tags lambda.norpc -o bootstrap ./cmd/publisher
```

- `provided.al2023` ランタイムではバイナリ名が `bootstrap` 固定
- `arm64` は x86 より安価で、Go では移植性の問題もほぼ発生しない
- `-tags lambda.norpc` で不要な RPC 依存を除外できる

## 9. 実装ステップ

### 第0段階: 外部依存の確認(最優先)

自分の作業速度で短縮できない工程を先に着手する。

- **SES の本番アクセス申請**(サンドボックス解除には AWS 側の審査待ちが発生する)
- **送信ドメイン認証の DNS レコード追加**(DKIM / SPF / DMARC)
- **天気 API の実地検証**(前提が崩れるとイベント設計から見直しになる)

### 第1段階: ドメインロジックの実装

AWS に触れず Go だけで完結する部分。SES の審査待ち期間に進められる。

- 天気 API レスポンスを `Forecast` 値オブジェクトへ変換する
- 降水確率が閾値以上の連続した時間帯を1区間にまとめる判定ロジック
- ユーザーとチャネルから通知イベントを組み立てる処理

テストが最も書きやすい領域。API レスポンスの JSON を固定データとし、境界値(日をまたぐ降雨、確率が閾値ちょうど、データ欠損)を机上で検証する。ユーザーはハードコードで構わないが、`[]User` を受け取るシグネチャにしておくと第3段階での移行が楽になる。

### 第2段階: 最小構成で縦に1本通す

```
EventBridge Scheduler → Lambda → SES
```

RDS も EventBridge バスも SQS も入れない。ユーザーと都市はハードコード。デプロイ・IAM・Lambda ランタイム・SES 疎通という切り分けの難しい領域を一度に検証する。第1段階のコードに Lambda のハンドラという殻をかぶせる作業に相当する。

**このタイミングで IaC のツールを決定する。** 2つ目のスタックを書き始めてからの乗り換えは手戻りが大きい。

### 第3段階: RDS と VPC の導入

最もハマりやすい工程。ネットワークの問題はタイムアウトするだけでエラーメッセージが出ないことが多いため、第2段階で「Lambda 自体は動く」ことを確認済みにしておく価値がある。

- VPC、サブネット、ルートテーブル、NAT Gateway
- セキュリティグループ(Lambda → RDS)
- Secrets Manager からの認証情報取得
- コネクション管理の設定

NAT Gateway は課金が発生するため、動作確認後に不要であれば削除する運用も検討する。

### 第4段階: 非同期化

```
Lambda(発行) → EventBridge バス → ルール → SQS → Lambda(送信) → SES
```

第3段階までで層分けができていれば、`main.go` とハンドラの差し替えが中心になる。ここで分解が困難であれば、第1〜3段階の層分けが不十分だったというフィードバックになる。

### 第5段階: 異常系の担保

正常系が動作していないと検証できないため最後に実施するが、本番でユーザーへ送信を開始する前には必須。

- 冪等性テーブルと重複送信の防止
- `ReportBatchItemFailures` による部分バッチ処理
- DLQ とアラーム
- SES のバウンス / 苦情の受信とチャネル無効化

特にバウンス処理を入れずに送信を続けると、SES の評判指標が悪化しアカウント単位で送信停止となるリスクがある。

## 10. 将来の拡張

### push 通知の追加

EventBridge のルール、SQS キュー、送信 Lambda を1組追加する。発行側とメール経路には変更を加えない。イベントの payload が意味的なデータのままであることが前提となる。

### フロントエンド(管理画面)の追加

CloudFront に2つのビヘイビアを持たせ、単一オリジンに統合する構成を推奨する。

```
ブラウザ → CloudFront ┬ 既定ビヘイビア → S3(静的アセット)
                      └ /api/*        → API Gateway → Lambda → RDS
```

- CORS 設定が不要になり、Cookie ベースのセッションも素直に成立する
- 認証は Cognito User Pool と API Gateway の JWT オーソライザに委譲し、Lambda 側に認証ロジックを持ち込まない
- OpenAPI を単一の真実の源とし、`oapi-codegen` でサーバー型を、`openapi-typescript` でフロント型を生成する
- API 用関数は通知パイプラインから分離する(一斉配信中に同時実行数を奪われ API がスロットリングされることを防ぐ)

**未決事項:** ユーザー管理が「管理者が他人の設定を管理する」社内ツール型か、「各ユーザーが自分の設定を管理する」セルフサービス型かによって、Cognito と通知対象の関係およびデータモデルが変わる。push 通知のエンドポイント登録にも影響するため、早期に決定しておく価値がある。

### スケール時の分割

ユーザー数や都市数の増加により処理時間が問題になった場合、都市単位のイベント発行を挟む。

```
Lambda A: 都市ごとに予報取得 → 「都市の予報が確定した」イベント発行
Lambda B: 該当都市のユーザーを取得し、通知イベントに展開
```

都市単位で並列化でき、1実行あたりの処理時間が都市数に依存しなくなる。明確にスケールの問題が出てから導入する。

### 外部 API のキャッシュ化

通知とは独立したスケジュールで予報を取得し、DynamoDB や S3 にキャッシュする方式。通知の実行パスから外部 API 依存が消えるため、配信時刻に API が停止していても直近データで配信できる。ドメイン層から見れば `ForecastRepository` の実装が差し替わるだけであり、移行は局所的に済む。
