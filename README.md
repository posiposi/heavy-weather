# heavy-weather

毎朝、その日の天気と「雨が降りそうな時間帯」をユーザーに届ける通知システム。
サーバーレスアーキテクチャのキャッチアッププロジェクトとしている。

## 何をするものか

ユーザーは自分の住む都市を登録しておく。システムは毎朝決まった時刻に起動し、登録された都市の予報を取得して、その日の気温と降雨が見込まれる時間帯をまとめてメールで配信する。

「今日は傘が要るか、要るなら何時ごろか」が朝の時点で分かることを目的とする。

## 設計の考え方

### 通知の「発行」と「送信」を分ける

システムは大きく2つの役割に分かれている。

**発行側**は「誰に、何を伝えるべきか」を決める。ユーザーの購読情報を読み、必要な都市の予報を取得し、通知すべき内容を1件ずつのメッセージとして組み立てて送り出す。

**送信側**は「それをどう届けるか」を担う。受け取ったメッセージを実際の配信物（メール本文など）に整形し、配信する。

両者はメッセージを介して繋がっており、直接呼び合わない。発行側が止まっても送信済みの分は届き、送信側が詰まっても発行側は影響を受けない。

### メッセージには「意味」だけを載せる

発行側から送信側へ渡されるメッセージには、完成した文面を含めない。都市・日付・気温・降雨時間帯といった**意味としてのデータ**だけを載せ、それを人が読む形に整えるのは送信側の仕事とする。

この分離により、将来プッシュ通知を足すときも、発行側には手を入れずに済む。メールは長い文面に、プッシュは短い一行にと、届け方ごとに整形すればよい。

### 同じ通知を二度送らない

非同期な仕組みでは、同じメッセージが複数回届きうる。そのため通知は**内容から一意に決まる識別子**を持ち、送信前にその識別子で「もう送ったか」を確認する。再実行しても識別子は変わらないため、重複配信を防げる。

### 部分的な失敗を許容する

外部の予報サービスは常に応答するとは限らない。ある都市の取得に失敗しても全体を止めず、取得できた分だけ配信する方針をとる。天気通知という性質上、「全員に届かない」より「一部に届く」ほうが望ましいという判断による。

### 届かなかったことを検知する

メールアドレスが無効であるなど、配信できなかった事実はシステムに返ってくる。これを受け取って該当ユーザーの通知先を無効化する仕組みを持つ。無効な宛先へ送り続けると、送信そのものが行えなくなるリスクがあるため、正常系と同じく必須の要素として扱う。

## 技術的な方針

| 項目 | 方針 |
|---|---|
| 言語 | Go |
| 実行基盤 | AWS。可能な限りサーバレスを指向する |
| データストア | リレーショナルデータベース。アクセスパターンが未確定であることと、データが本質的に関係を持つことによる |
| 起動方式 | スケジュール実行。将来のユーザーごとの配信時刻変更も同じ仕組みの延長で扱える方式を選ぶ |
| 配信経路 | 現時点ではメールのみ。プッシュ通知は経路を1組追加するだけで足せる構造にしておく |
| フロントエンド | 当面なし。将来的に管理画面を追加する可能性がある |

## コードの構成方針

「Lambda のプロジェクト」ではなく「Lambda にもデプロイできる Go アプリケーション」として扱う。

- **ビジネスロジックは実行環境を知らない。** 降雨時間帯の判定のような中核のロジックは、クラウドの都合から独立させる。ここが特定の実行基盤に依存し始めたら、設計が壊れ始めた合図とみなす
- **役割を分けてもロジックは共有する。** 分かれるのは入口だけで、その内側は共通のコードを参照する
- **アプリケーションとインフラ定義を同じリポジトリに置く。** この規模では両者が同時に変わることが多く、分けると変更が分断される

## ローカル開発環境

Go と MySQL を `docker compose` で立ち上げる。ホストに Go や MySQL を入れる必要はない。

| 用途 | イメージ |
|---|---|
| Go | `golang:1.26.6-bookworm` |
| MySQL | `mysql:8.4.10` |

Go は alpine ではなく Debian ベース（bookworm）を使う。alpine は musl libc であり、本番の Lambda ランタイム `provided.al2023`（glibc）と揃わないため、切り分けの難しい差異が生まれる。

### 起動

```sh
cp .env.example .env
docker compose up -d
```

`db` のヘルスチェックが healthy になるまで `app` は起動を待つ。初回はイメージの取得と MySQL の初期化で数十秒かかる。

### 使い方

```sh
docker compose exec app go test ./...   # テスト
docker compose exec app go build ./...  # ビルド
docker compose exec app go vet ./...    # lint
# DB に接続（パスワードはコンテナ内のシェルで展開させる）
docker compose exec db sh -c 'mysql -u "$MYSQL_USER" -p"$MYSQL_PASSWORD" "$MYSQL_DATABASE"'
```

モジュールキャッシュ（`/go/pkg/mod`）とビルドキャッシュは名前付きボリュームに置いてあるため、コンテナを作り直しても再ダウンロード・再ビルドは発生しない。MySQL のデータも同様に永続化される。

### 停止・破棄

```sh
docker compose down     # 停止（データは残る）
docker compose down -v  # ボリュームごと破棄（DB を初期状態に戻す）
```

### ポート

| サービス | ホスト側 | 用途 |
|---|---|---|
| `app` | `127.0.0.1:${APP_PUBLISHED_PORT}`（既定 8080） | ドメインロジックをブラウザや `curl` から動作確認するための入口 |
| `db` | `127.0.0.1:${DB_PUBLISHED_PORT}`（既定 3306） | GUI クライアント等からの接続 |

`app` のポートは開けてあるが、現時点で待ち受けるプロセスはない。第1段階でドメインロジックを手で叩いて確認したくなった時点で、`cmd/` 配下に動作確認用の HTTP サーバーを追加する。

その際、**コンテナ内では `0.0.0.0`（Go では `":"+port`）にバインドする**こと。`127.0.0.1` にバインドするとコンテナのループバックに閉じてしまい、ポートマッピングを通ってもホストから到達できない。待ち受けポートは `APP_PORT` から読む。

### 接続情報

`.env` で渡す。`.env` は Git 管理外なので、各自 `.env.example` からコピーして使う。ホストの 3306 が埋まっている場合は `DB_PUBLISHED_PORT` を変更する。公開先は `127.0.0.1` に限定してあるため、同一ネットワークの他端末からは接続できない。

MySQL の文字セット・タイムゾーン・`wait_timeout` は `compose.yaml` の `db.command` で mysqld の起動オプションとして明示している。設定ファイルに切り出すほどの分量ではないため。

`db` に `LANG=C.UTF-8` を渡しているのは、`mysql` クライアントが接続時の文字セットをロケールから決めるため。未設定だと latin1 にフォールバックし、CLI から日本語を投入すると文字化けする。タイムゾーンを UTC 固定にしているのは、Lambda の実行環境が既定で UTC であり、ローカルだけ JST だと時刻の扱いの誤りが表面化しないため。

## 現在の状況

**設計フェーズ。実装コードはまだ存在しない。**

実装は段階を追って進める方針をとる。まず外部サービスの利用申請など待ち時間の発生する手続きに着手し、その間にクラウドへ依存しないロジックを固める。次に最小構成で全体を一度貫通させ、そのうえでデータベースや非同期化といった要素を順に足していく。異常系の作り込みは正常系が動いてからでないと検証できないため最後に置くが、実際にユーザーへ配信を始める前には必須とする。

詳細は設計書の「実装ステップ」を参照。
